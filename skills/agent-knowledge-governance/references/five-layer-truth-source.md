# 五层真相源：结构、写入权与映射方法

> 一套能被多个智能体共用的知识库，必须区分**什么可以改、什么不能改**。
> 五层模型给的是**职责与写入权的分离**，不是固定的目录名。

---

## 1. 五层定义

| 层 | 名称 | 职责 | 写入权 | 可变性 |
|:--:|---|---|---|---|
| **00** | 资源层 | 原始证据、原始素材、原始响应 | **只读** | 🚫 任何人不得覆盖 |
| **01** | 主题 Wiki | 稳定知识、方法、案例、技能卡 | 产出该卡的 agent | 🔄 演进不覆盖（version+1） |
| **02** | 项目库 | 正在推进的问题、项目、决策 | 项目负责 agent | ✏️ 活跃可变 |
| **03** | 输出库 | 可实际使用的正式成果 | 项目负责 agent | ✏️ 批次化归档 |
| **04** | 系统维护层 | 入口、规则、状态、反馈、日志 | **单一写者** | 🔄 索引者统一聚合 |

---

## 2. 每层的关键约束

### 00 资源层：永远只读

原始素材一旦入库就冻结。任何加工都在上层做，**不回写原文件**。

**为什么要保护**：原始素材是所有结论的证据基底。一旦被覆盖，
「这个结论是从哪来的」就永远无法回答。

**保护手段**：
- 目录级只读权限（`chmod -R a-w`）
- 文件头标记（`<!-- RAW: read-only -->`）
- 质量闸门第 1 项专查「资源层零覆盖」

### 01 主题 Wiki：演进不覆盖

改内容时 `version + 1`，旧版进归档区，**永不删除历史结论**。

理由：三个月后你会想知道「当时为什么这么判断」，而那个判断的依据可能已被推翻。

**冲突处理**：同名经验以 version 升级取胜，旧版 archived，不静默覆盖。

### 02 项目库：活跃可变

正在推进的东西，允许频繁改。但**决策要单独成卡**（决策卡模板），
不能只写在日志流水里 —— 否则半年后无法追溯「为什么当时那么定」。

### 03 输出库：批次化

```
成果/
├── 2026-11-06_首次发布/
│   ├── 01_主产物.md
│   ├── 02_附属.md
│   └── raw/                    ← 原始素材（00 层性质，只读）
└── 2026-11-20_迭代版/
```

**每个批次一个目录，日期前缀**。批次内区分「草稿 / 候选 / 正式」三态，
但**只有正式态进最终索引**。

### 04 系统维护层：单一写者

中央总索引由**一个指定 agent**每日聚合更新。其他 agent 提交条目到待办区，
不直接改中央索引。

原因：多智能体并发写同一文件必然冲突。

## 3. 映射到你现有的目录结构

**不要照搬五层的目录名**。关键是把现有的目录**映射**到五层职责上。

### 映射方法

1. 列出你现有的所有顶层目录
2. 对每个目录问三个问题：
   - 它会被覆盖吗？→ 是 → 属于 00（应只读）或 03（产出）
   - 它会被多个 agent 写吗？→ 是 → 属于 04（需单一写者）
   - 它的内容会长期演进吗？→ 是 → 属于 01（版本化不覆盖）
3. 标注「职责错配」的地方 —— 通常是「日志目录里混了知识结论」

### 典型错配与修正

| 症状 | 错配 | 修正 |
|---|---|---|
| 改 A 项目时误改了 B 项目的结论 | 01 层的知识混在 02 层的项目里 | 通用结论抽到 01；项目日志只留过程 |
| 多个 agent 同时改总索引打架 | 04 层没有指定单一写者 | 指定一个 agent 每日聚合 |
| 原始截图被「优化」后找不到原版 | 00 层没保护 | 加只读标记 + 闸门第 1 项 |
| 结论被直接改写，说不清怎么演进的 | 01 层没有版本化 | version + 1 + 旧版归档 |

## 4. 迁移路径（不破坏现有）

**渐进式融合**，不要大爆炸式重构：

```
第一阶段（不动结构）
  ✅ 写映射文档：现有目录 ↔ 五层职责
  ✅ 建 00 资源层的只读标记
  ✅ 给已有卡片补 frontmatter
  ✅ 明确 04 层的单一写者是谁

第二阶段（补机制）
  🟡 建反馈库 + 进化提案目录
  🟡 上线质量闸门脚本
  🟡 建立版本号管理

第三阶段（按需优化）
  ⏳ 拆分混杂目录
  ⏳ 抽离通用结论到 01 层
  ⏳ 自动化索引聚合
```

**每阶段之间要有明确验收**（断链 0 + 孤儿 0 + 闸门 0 FAIL），
不达标不进入下一阶段。

## 5. 层级间的引用方向

```
00 资源层  ←── 引用（作为证据来源）
01 主题Wiki ←── 引用（提炼结论）
02 项目库  ←── 引用（活跃上下文）
03 输出库  ←── 引用（最终成果）
04 系统维护 ←─ 引用（索引与规则，反向聚合全部）
```

**引用方向是单向的**：上层引用下层，下层不反向引用上层。

例外：04 层的索引会聚合所有层的链接 —— 那是**索引行为**，不是内容引用。

## 6. 与 frontmatter 的对应

每层的卡片字段要求不同：

| 层 | type 取值 | 特殊字段 |
|---|---|---|
| 00 | `原始资料` | `source`、`type`、`confidence`、`sensitivity`、未读标注 |
| 01 | `知识卡` | `confidence`、`related` |
| 02 | `项目卡` `决策卡` | `status`（进行中/已完成/阻塞/已归档） |
| 03 | `成果卡` | 批次目录、交付索引 |
| 04 | `反馈卡` `进化提案` | `status`、`target_rule`、`evidence_count` |

**「未读冒充已读」是 FAIL** —— 00 层的素材如果标了已读但实际没读，后续结论就不可信。

## 7. 自检问题

部署完成后问自己：

1. **我能说出每一层谁有写权吗？** 说不出来 = 边界没划清
2. **资源层真的只读吗？** 试改一下，改不动才算
3. **中央索引有且只有一个写者吗？**
4. **跨层引用方向对吗？** 有反向引用 = 层级混了
5. **迁移分阶段了吗？** 一步到位 = 风险太高
