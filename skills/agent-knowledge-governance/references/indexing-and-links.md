# 索引与 wikilink 规范

> 目标：**索引与实际文件永远一致，图谱里没有散落节点。**

---

## 1. 禁止独立索引文件（最容易被违反的规则）

### 规则

> **除非跨项目资源，否则禁止新建 `文件索引.md` / `图片索引.md` / `XX清单.md` 这类独立 MD。
> 必须通过已有项目索引的内嵌 wikilink 关联。**

### 为什么

Obsidian 的图谱视图里，**每个独立索引文件都是一个孤立入口节点**。
几十个索引文件 = 几十个散落节点，图谱彻底失去意义。

而且独立索引文件本身会**分裂引用**：一个内容被 5 个独立索引引用，
但这 5 个索引之间互不连通 → 图谱上依然散落。

### 正确做法

```markdown
<!-- ❌ 错误：新建 图片索引.md，内容散在独立文件里 -->
图片索引.md:
- [[图1]]
- [[图2]]

<!-- ✅ 正确：在已有的项目 00_索引.md 里加行 -->
00_索引.md:
## 本目录图片
- [[图1]] —— 封面图
- [[图2]] —— 证据截图
```

**例外**：真正跨项目的资源（如全库通用的「知识卡模板」「术语表」）才可以建独立索引。

## 2. 孤儿文件（Orphan）必须清零

### 定义

在 vault 中存在，但**没有任何其他文件通过 wikilink 指向它**的文件。

### 规则

> **任何时候孤儿文件数 > 0，必须立即执行修复流程。不允许「稍后再修」。**

理由：孤儿文件在图谱上是散点，而且**不会被任何索引检索到** —— 等于不存在，
但又占着存储和注意力。

### 修复流程

```bash
python3 scripts/check_orphans.py <vault-root>
```

输出形如：

```
扫描 9885 个 md 文件
入链统计中...
孤儿文件 (3):
  商业与内容创作/某个临时笔记.md
  归档与变更/旧草稿.md
  产品技术项目/未归档素材.md
```

**逐个处理，只有三种正确处置**：

| 情况 | 处置 |
|---|---|
| 有价值，只是没挂上 | 在**已有的**项目索引里加 wikilink |
| 与某张主卡重复 | 合并进主卡（独有内容并入），旧文件进归档区 |
| 确实是废弃草稿 | 移出 vault（git 里有历史，不是回收站） |

**没有第四种处置**。「先放着」不是处置。

### 批量操作注意

新建/移动文件时，**同一批次内**就完成索引登记，不要攒到最后 ——
攒到最后你就已经忘了这个文件属于哪个索引。

## 3. 断链（Broken Link）扫描

### 与孤儿的区别

| | 孤儿 | 断链 |
|---|---|---|
| 含义 | 文件存在，但没人引用它 | 引用指向不存在的文件 |
| 症状 | 图谱散点、检索不到 | 点开是空白页 |
| 常见成因 | 忘记登记索引 | 批量移动文件时只改了路径 |

### 脚本

```bash
python3 scripts/check_links.py <vault-root>
```

### 批量移动的正确姿势

**永远不要用 `mv` 移动一批文件后就跑质量闸门了事** —— 一定会断链。

正确顺序：

```bash
# 1. 先备份
cp -R <目录> /tmp/kb_batchN_backup-<时间戳>

# 2. 移动文件
mv <旧目录> <新目录>

# 3. 批量替换 wikilink 前缀（用脚本，不要手改）
python3 - <<'EOF'
import pathlib, re
OLD, NEW = "旧目录名/", "新目录名/"
root = pathlib.Path("<vault-root>")
n = 0
for md in root.rglob("*.md"):
    if ".obsidian" in md.parts: continue
    s = md.read_text(encoding="utf-8")
    if OLD in s:
        md.write_text(s.replace(OLD, NEW), encoding="utf-8")
        n += 1
print(f"更新 {n} 个文件")
EOF

# 4. 断链扫描 + 孤儿扫描
python3 scripts/check_links.py <vault-root>
python3 scripts/check_orphans.py <vault-root>

# 5. 质量闸门（0 FAIL 才算完）
bash scripts/quality_gate.sh <vault-root>
```

**注意**：用 `while IFS= read -r` 遍历，不要用 `for f in $(find ...)` ——
后者会在文件名含空格时丢文件（这是真实踩过的坑）。

## 4. frontmatter 契约

### 完整字段

```yaml
---
title: <卡片标题>                    # 必填
type: <知识卡|项目卡|决策卡|成果卡|反馈卡|进化提案|实践笔记>   # 必填
status: <active|draft|archived|blocked>          # 必填
owner: <负责人>                      # 建议
created: YYYY-MM-DD                  # 必填
updated: YYYY-MM-DD                  # 必填
source: <来源URL|路径|会话ID>          # 必填
confidence: <high|medium|low>         # 建议
sensitivity: <public|internal|confidential|secret>  # 建议
version: 1.0                         # 建议
effective_date: YYYY-MM-DD            # 建议
review_date: YYYY-MM-DD               # 建议（默认 effective_date + 90 天）
tags: [tag1, tag2]                    # 必填
related: ["[[卡A]]", "[[卡B]]"]         # 建议
---
```

### 最低要求

`title` / `type` / `status` / `created` / `updated` / `source` / `tags`

质量闸门会检查其中若干项（source 标注、type 标注覆盖率、日期有效性）。

### title 的写法

- **带域前缀**：`微信运营/公众号排版规范` 而不是 `排版规范`
- 前缀用 `/` 分隔，不用空格
- 避免标点符号（`：` `，` 会影响 URL 和搜索）

## 5. 版本语义化

| 变更类型 | 版本 | 动作 |
|---|---|---|
| 小修（错别字、补充链接） | `1.0 → 1.1` | 在原文件改，`version` +1 |
| 内容重构（结构变了） | `1.x → 2.0` | 新版本文件 + 旧版进归档区 |
| 合并其他卡 | 主卡 `version` +1 | `source` 字段注明所有被合并文件名 |
| 结论被推翻 | `2.0 → 3.0` | **不删除旧版**，进归档区并注明推翻关系 |

**关键**：结论演进**永不覆盖**。旧版进 `归档与变更/<域>/版本历史/`。

理由：三个月后你会想知道「当时为什么这么判断」，而那个判断的依据可能已被推翻。
保留历史比保持整洁重要。

## 6. 索引更新时机

| 事件 | 动作 |
|---|---|
| 新建 L1 成果 | **立即**在项目索引加 wikilink（不攒） |
| 合并卡片 | 更新主卡的 `source` + `related`，旧卡移归档 |
| 移动文件 | 批量替换 wikilink 前缀 → 断链扫描 → 孤儿扫描 |
| 新增业务域 | 域名加进总导航 MOC |
| 每日聚合 | 中央总索引由**单一写者**统一更新 |

### 单一写者原则

中央索引（如 `00_总导航.md`）**只能由一个指定 agent 每日聚合更新**。
其他 agent 把条目提交到各自的待办区，不直接改中央索引。

原因：多智能体并发写同一文件必然产生冲突和丢失。

---

## 7. 索引质量的三个自检问题

写完索引后问自己：

1. **一个新来的 agent 只读索引，能找到这个内容吗？** → 找不到就是索引无效
2. **图谱视图里有没有散落节点？** → 有就是孤儿没清
3. **点开任何一个 wikilink，会 404 吗？** → 会就是断链

三个问题的答案应当分别是「能」「没有」「不会」。
