# 经验回流协议：让任一 agent 都能调用历史经验

> 解决的核心问题：**豆包 / Codex / Trae / Hermes / WorkBuddy 各干各的，
> 处理同类问题时经验不互通，重复踩坑。**

---

## 1. 为什么必须显式设计

多智能体协作有一个隐蔽的陷阱：每个 agent 都很聪明，但**它们的记忆彼此隔离**。

Agent A 花了两小时发现「WordPress XML-RPC 传 content 会丢字段」，写进了自己的项目日志。
三个月后 Agent B 处理同类任务，**从零开始**，又踩一遍。

这不是能力问题，是**记忆架构问题**。解法不是「让 agent 更聪明」，
而是**把经验从 agent 内部搬到共享载体上**。

---

## 2. 四步闭环

```
① 沉淀   任一 agent 产出可复用结论
          → 清洗为单主题知识卡（去项目特定词、抽通用结论）
          → 归入对应业务域
                ↓
② 加载   每个 agent 启动时按 AGENTS.md 加载链
          → 额外读：知识库总导航 MOC + 各域索引 + 本包
          → 获得同一份记忆
                ↓
③ 双向索引  卡与卡用 [[wikilinks]] 互链（Obsidian 自动生成反向链接）
          + frontmatter 的 related 字段
          + MOC 串起全库
          → 任一 agent 通过索引即可反查「过去怎么处理过同类问题」
                ↓
④ 查询作答  交互时先检索相关域索引与卡
          → 把历史经验作为上下文再作答
          → 并标注「参考了哪张卡」
```

**第 ④ 步的「标注出处」是硬要求**。不标注，读者无法判断结论的来源与可靠性，
也无法在结论出错时追溯修正。

---

## 3. 加载链：写进各 agent 的 AGENTS.md

```markdown
## 启动时加载（每次会话开始前）

1. 读本 agent 的 `AGENTS.md`（边界与职责）
2. 读 `知识库架构/00_知识库总导航-MOC.md`（全库地图）
3. 读本业务域的 `00_索引.md` + 相关域的实战经验索引
4. 读本项目的 `索引.md` + `经验教训.md` + 会话索引
5. 产出「已覆盖 / 待补充 / 可复用」三栏现状对齐

## 收尾时回流（每次会话结束前）

1. 过程 → 项目 `日志.md`
2. 坑 → 项目 `经验教训.md`（现象 → 原因 → 对策）
3. 可复用结论 → 知识卡 → 域索引登记
4. L1 产物 → `成果/<批次>/` + 项目索引 wikilink
5. 跑质量闸门（0 FAIL 才算完）
```

## 4. 责任与冲突

| 项 | 规则 |
|---|---|
| **卡的 owner** | 产出该卡的 agent |
| **reviewer** | 默认人类负责人；确认后 `status: active` |
| **同名冲突** | 以 `version` 升级，旧版 `archived` 进归档区，**不覆盖结论** |
| **谁改总索引** | 单一写者（每日聚合），其他 agent 提交条目 |

### 清洗规则：什么该变成知识卡

写卡片时把**项目特定的东西剥掉**，只留通用部分：

```
❌ 「在 bestaitoolsite.com 项目里，WP REST 改 trash 时 PUT 报 400」
✅ 「WP REST API 改文章状态用 POST 而非 PUT；改 trash 会返回 400」

❌ 「本次口播的第 3 段音频有杂音」
✅ 「口播录音前先录 10s 静音底噪，供降噪算法参考」
```

判断标准：**换一个项目，这句话还成立吗？** 成立 → 知识卡；不成立 → 项目日志。

## 5. 落库判定：两步法

对每一个待入库的文件：

### 步骤 1 · 业务域关联
问：**这份内容能否挂到某个业务域？**
- 能 → 步骤 2
- 不能（纯工具 / 环境 / 第三方代码 / 应用数据 / 重复备份）→ **不进库**，
  记录在数据源盘点的「排除」列，物理留存原位

### 步骤 2 · 版本比对 / 活跃度判定
取该文件（或同类内容最新版本）的 `mtime`：

```
基准：近 1 个月 = mtime ≥ (今天 − 30 天)

mtime ≥ 阈值  → 进活跃业务域 <业务域>/<细分项目>/
mtime < 阈值  → 作为该业务域的细分项目进 归档与变更/<业务域>/（静态快照，不删）
```

vault 内既有的、长期未动的旧笔记，亦按此阈值判定是否移入 `归档与变更/`。

## 6. 双向索引的实操

```markdown
# 知识卡 frontmatter
---
title: WP REST API 改文章状态用 POST
type: 知识卡
status: active
owner: Codex
source: bestaitoolsite运营/项目成果/2026-10_WP发布流水线复盘
related: ["[[WordPress 自动发布流水线]]", "[[REST API 常见错误码]]"]
tags: [wordpress, rest-api, wp-cli]
---
```

**Obsidian 的反向链接是自动的** —— 只要有 `[[链接]]`，被链接页的「反向链接」面板就会出现来源。
这意味着**只要一张卡被引用过一次，它就不会成为孤儿**。

## 7. 效果验证

回流机制是否真的起作用，看三个指标：

| 指标 | 怎么看 | 健康值 |
|---|---|---|
| **重复踩坑率** | 新增知识卡中，有多少条是「以前踩过但没沉淀」 | 逐月下降 |
| **卡片的被引用次数** | Obsidian 反向链接面板 | 有实际使用的卡 > 70% |
| **孤儿率** | `check_orphans.py` 输出 | 恒为 0 |

**注意**：不要用「卡的数量」当指标 —— 卡片越多不等于经验共享越好。
一个只有 30 张卡但每张都被反复引用的库，比 500 张无人问津的卡有用得多。

## 8. 常见失败模式

| 失败 | 表现 | 修复 |
|---|---|---|
| 沉淀门槛过高 | 什么都想沉淀，最后什么都不沉淀 | 用「换个项目还成立吗」一刀切 |
| 只写不引 | 卡片很多，但从没被检索到 | 开工前强制读域索引 |
| 不标注出处 | 结论无法追溯，出错难修 | 第④步强制标注来源卡 |
| 各 agent 口径不一 | 同一件事三个名字 | 统一项目名 + wikilink 互链 |
| 卡片不更新 | 旧结论一直有效，实际已过时 | `review_date` + 到期审计 |
