# 反馈闭环：从吐槽到规则的受控演化

> **铁律：除事实错误和安全问题外，一次反馈不得直接改全局规则。**
> 必须经 **聚类 → 版本化 → 批准 → 对照** 四步。

---

## 1. 为什么不能「听到一次就改」

多智能体协作里，智能体最容易犯的错是**过度服从** —— 用户随口一句抱怨，
它就立刻把全局规则改了。后果：

1. **规则集膨胀**：每次吐槽产生一条规则，几十次后规则互相矛盾，没人会读
2. **单次异常被固化**：可能只是那次的特例（网络抖动、临时需求、心情不好）
3. **无法回溯**：规则为什么变成这样，没人知道
4. **推翻成本高**：改回去又要走一遍流程

**正确的路径**：反馈先**记录**，同类反馈**重复出现**才认定为**规律**，
规律变成规则前必须**人批准**，执行后要**对照验证**。

---

## 2. 例外：两类反馈立即修

| 类型 | 例子 | 为什么不等 |
|---|---|---|
| **事实错误** | 数据算错、引用的来源不存在、说错的日期 | 事实错误会直接误导后续所有决策 |
| **安全问题** | 凭据入库、危险命令、隐私泄露 | 风险不等第二次 |

---

## 3. 反馈分类

### 按性质

| 类型 | 含义 | 示例 |
|---|---|---|
| **正反馈** | 用户认可成果 | 「这个分类很好」 |
| **负反馈** | 用户批评成果 | 「这个标题不行」 |
| **缺口** | 发现遗漏 | 「还应该包含 XXX」 |
| **结果数据** | 实际效果 | 「发布后阅读量 500」 |

### 按对象

| 对象 | 范围 | 修改什么 |
|---|---|---|
| 事实 | 来源、引用、数据 | 立即修 |
| 判断 | 推理、结论 | 走提案 |
| 方法 | 流程、步骤 | 走提案 |
| 结构 | 框架、层次 | 走提案 |
| 表达 | 文风、措辞 | 走提案 |
| 风险 | 合规、安全 | 立即修 |
| 格式 | 排版、样式 | 走提案 |

### 按强度

| 强度 | 判据 | 触发 |
|:--:|---|---|
| 一次 | 单次反馈 | 仅记录 |
| 重复 | ≥2 次同类反馈 | **触发进化提案** |
| 结果数据 | 有客观数据支撑 | **立即触发提案** |

## 4. 记录：反馈卡

```
<项目>/反馈/feedback-<YYYY-MM-DD>-<编号>.md
```

**必须保留用户原话** —— 后续聚类时，转述过的反馈会丢失关键信息。

```markdown
---
type: feedback
version: 1.0
created: YYYY-MM-DD
project: <项目名>
session_id: <session_id>
feedback_id: feedback-YYYY-MM-DD-001
status: recorded
---

# 反馈 · <日期> · <主题>

## 原始反馈（保留原话）

> 用户原话：<quote>
> 反馈对象：<具体成果/方法/规则>
> 反馈时间：YYYY-MM-DD HH:MM

## 反馈拆解

| 维度 | 值 |
|---|---|
| 类型 | <正/负/缺口/结果> |
| 对象 | <事实/判断/方法/结构/表达/风险/格式> |
| 范围 | <本成果/同类任务/全局> |
| 强度 | <一次/重复/结果数据> |
| 建议动作 | <立即修事实错误/只记录/提出进化提案> |

## 历史对比（如有）

| 日期 | 反馈 | 类型 | 处理 |
|---|---|---|---|

## 处理决定

- [ ] 立即修（仅事实错误/安全问题）
- [ ] 记录待聚类（待 ≥2 次重复）
- [ ] 提交进化提案（如已是重复或结果数据）
```

## 5. 聚类：周进化流程

### 触发

- 每周固定时间（建议周日 20:00）
- 或达到阈值时随时触发

### 五步流程

```
Step 1  读取最近 7 天所有 feedback
Step 2  聚类相似反馈（按「对象 + 场景」聚，不按字面相似）
Step 3  检查是否 ≥2 次重复 或 有结果数据
Step 4  满足 → 生成进化提案
Step 5  不满足 → 记录「本周无可验证进化」
```

**Step 5 也要写进报告** —— 「本周没有变化」是一条有价值的信息，
说明现有规则在当前场景下够用。

### 聚类的正确粒度

```
❌ 过度聚类：「标题不好」和「标题太长」聚成一类
✅ 正确聚类：「标题风格不匹配受众」（标题不好 + 标题太长 + 标题像广告）

判断标准：聚到一起的反馈，**用同一条规则能同时解决吗？**
能 → 同一类；不能 → 拆开
```

## 6. 提案：改全局规则前必填

```
智能体/Hermes/进化提案/evolution-<YYYY-MM-DD>-<主题>.md
```

模板见 `templates/evolution-proposal.md`。必填项：

| 区块 | 内容 | 为什么必填 |
|---|---|---|
| **触发证据表** | 反馈 ID + 日期 + 类型 + 强度 + 摘要 | 证明不是单次异常 |
| **旧规则原文** | 注明版本号 + 文件路径 + 具体内容 | 让人能对比 |
| **新规则内容** | 可直接替换的文本 | 批准后能立即执行 |
| **影响评估** | 范围 / 风险 / 观察周期 / **回滚方案** | 没回滚方案 = 不能改全局规则 |
| **用户批准** | 勾选框 | **未批准不执行** |
| **执行记录** | 批准后只在原文件 `version + 1`，不覆盖原内容 | 保留历史 |
| **前后对照表** | 旧行为 / 新预期 / 实测差异 | 验证有效性 |

### 风险分级

| 风险 | 范围 | 审批 |
|---|---|---|
| 低 | 仅影响单个成果 | 可由 owner 批准 |
| 中 | 影响同类任务 | 需人类负责人批准 |
| 高 | 影响全局规则 | 需人类负责人批准 + 必须有回滚方案 |

---

## 7. 执行与对照

### 执行规则

```
批准后：
  1. 在**原文件**上修改，version + 1
  2. 不删除旧内容（除非是明确的错误）
  3. 在 CHANGELOG 记录变更
  4. 保留旧版快照到归档区
```

### 对照验证

观察周期到了，做一次前后对照：

| 维度 | 旧规则行为 | 新规则预期行为 | 实测差异 |
|---|---|---|---|
| 例：标题长度 | 平均 32 字 | 15–20 字 | 改后平均 18 字 ✅ |

**没有实测差异 = 提案无效或执行不到位** → 回滚或重新提案。

```

├── 反馈库/                          ← 反馈卡
│   ├── feedback-2026-08-20-001.md
│   ├── 30天观察期计划-2026-08-21.md
│   └── 00_索引.md
├── 进化提案/
│   ├── evolution-2026-11-02_xxx.md
│   └── 00_索引.md
└── scripts/quality_gate.sh          ← 第 9、13 项检查这两个目录是否存在
```

**质量闸门第 9 项**：检查「抓取失败 ≠ 无新增」—— 反馈库已建立。
**第 13 项**：检查反馈库是否**有运行记录**（而不只是目录存在）。
**第 15 项**：画像长期无更新 → 触发审计。

## 9. 一个反面案例

```
用户说：「这次字体太小了」
→ 智能体立刻在全局规则里加了一条「所有正文 ≥ 28px」
→ 三个月后，所有文档都 ≥28px，包括那些本来就该更小的表格标注
→ 规则集多了一条没人理解的硬约束
```

**正确做法**：

```
① 记录：字体太小（对象=格式，强度=一次）
② 聚类：等第二次「太小了」出现
③ 提案：「正文阅读性字号 ≥ 28px（表格标注类除外）」
   —— 带适用范围，不是无差别
④ 批准：人类确认
⑤ 对照：观察 2 周，验证表格类没被误伤
```

## 10. 检查清单

写反馈卡时：

- [ ] 用户原话**逐字**保留（不转述、不美化）
- [ ] 拆解表填全（类型/对象/范围/强度/建议动作）
- [ ] 历史对比表查了（有没有同类反馈）
- [ ] 处理决定勾了（不是"待定"）

提进化提案时：

- [ ] 触发证据 ≥2 条，或有结果数据支撑
- [ ] 旧规则原文引用了（含版本号）
- [ ] 新规则有**适用范围**（不是一刀切）
- [ ] 影响评估填了，含**回滚方案**
- [ ] 用户批准勾了（**没勾不执行**）
- [ ] 执行后填了前后对照表
