# 证据先行与交棒闭环

> 回答两个问题：**怎么确认活真的做完了？** 以及 **怎么把活交出去而不丢？**

---

## 1. 核心区分：执行人报告 vs 独立核验

| | 执行人报告 | 独立核验 |
|---|---|---|
| 谁做的 | 干活的人自己说「好了」 | 收的人 / 指定核验人亲手看过 |
| 证据形态 | 附他自己的核法说明 | 亲手打开看、播放、重算、按原步骤再走一遍 |
| 地位 | **线索** | **证据** |
| 能否用来宣告完成 | ❌ 不能 | ✅ 能 |

**这一条是整份文档的地基**：所有「说做好了」的判断都必须建立在这条区分上。

---

## 2. 有效证据的定义

> 你（或指定的核验人）**亲手拿到的**，而且它核的**版本、范围、环境**，
> 和你现在要说的这句话**对得上**。

三个条件缺一不可：

| 条件 | 反例 |
|---|---|
| **亲手拿到** | 转述别人的报告 |
| **版本对得上** | 核的是旧版本 / 别的分支 |
| **范围对得上** | 只核了一部分，说的是全部 |
| **环境对得上** | 在 A 机器核的，说 B 机器也成立 |

### 复用与补核

| 情形 | 动作 |
|---|---|
| 上次核过、之后**没改过**、**没失败过**、**环境没换** | ✅ 可复用，写明「哪一次核的、哪个版本」 |
| 之后有改动 | ⚠️ 只补核**受影响的部分** |
| 之后有过失败 | ⚠️ 失败过的部分必须重核（失败可能污染后续） |
| 换了环境（换机器/账号/软件版本） | ⚠️ 重新核 |

**原则**：拿不准影响到哪，就把范围放大一点。多核一点成本低，漏核成本高。

### 不算证据的四类

```
❌ 别人说好了的
❌ 核的是旧版本或别的范围的
❌ 「应该没问题」
❌ 截图看起来对（没打开原文件对比）
```

## 3. 开口前的五步

```
1. 想清楚   哪件事能证明我要说的这句话？
2. 拿证据   有对得上当前版本的有效证据就复用（写明出处）
            没有就亲手完整做一遍（别人的报告只当线索）
3. 看完结果 整份看完，不只看开头几行
            有几处出错就数清几处（不「总体还行」）
4. 对照     这个结果真能撑住我要说的话吗？
            撑不住 → 照实说现在到哪一步，附上证据
            撑得住 → 说结论，附上证据
5. 再开口
```

**第 3 步是最容易偷懒的**。只看开头几行就宣布完成，是最常见的漏检方式。

---

## 4. 「想说什么 → 要什么证据」对照表

| 要说的话 | 必须拿到的证据 |
|---|---|
| 「文件已放到某处」 | 路径 + 文件确实存在（`ls`）+ 是约定位置 |
| 「功能已实现」 | 实际跑一次 + 看到预期输出 |
| 「bug 已修复」 | 复现步骤现在跑不出错 + 之前能复现（证明确实是这个 bug） |
| 「测试通过」 | 测试命令的完整输出 + 退出码 0 |
| 「文档已更新」 | 打开文件确认内容确实变了（不是只改了时间戳） |
| 「图片已生成」 | 打开图片看（不是只看文件大小） |
| 「视频已渲染」 | 播放关键帧（首/中/尾）+ 确认时长与音轨 |
| 「已发布」 | 线上地址 + 实际访问一次 + 确认内容正确 |
| 「数据已同步」 | 两边对账（条数/哈希/关键字段），不是只看一边 |
| 「无问题」 | 逐条对照原要求清单，每条给出对应证据 |

## 5. 该停一下的信号

出现以下任一情况，**停下来重新核**，不要继续往下汇报：

| 信号 | 含义 |
|---|---|
| 「应该没问题吧」 | 没看就下结论 |
| 「之前测过类似的」 | 这次的版本/环境可能不同 |
| 「改了很多地方，应该没影响这边」 | 改动的影响面往往比想象大 |
| 「脚本跑成功了」 | 跑成功 ≠ 结果正确（要看输出内容） |
| 「我先按常规做了」 | 常规不一定适用于这次 |
| 证据是**自己**的且任务由**别人**验收 | 该由收的人核 |
| 核验时间距今超过一次会话 | 期间可能变了 |

## 6. 交棒闭环：五状态分离

### 6.1 状态定义

| 状态 | 含义 | 在未完清单？ |
|---|---|---|
| `待收` | 活已派出（或开跑），还没人确认接下 | 在 |
| `已接单` | 执行人确认接下，**成果还没到** | 在 |
| `已收到成果` | 交付物到了约定位置，收的人看见了，**还没核** | 在（待核） |
| `已验收` | 核过了，可交下一棒或关闭 | **不在了** |
| `已取消` | 有权的人明确说不做了 | **不在了** |

过程行（不改变未完清单状态）：
- `续期` —— 新预计（不改原承诺）
- `升级` —— 过点没人接 / 到点没交 / 交了没核，追不上时
- `退回` —— 核了没过，需重交

### 6.2 三条必须写死的反模式

**① 等待结束 ≠ 成果回来**

> 后台命令停了、对方说「好了」，都要**去结果该在的地方看**；
> 看见了才记「已收到成果」，看不见就查是失败还是丢了 —— 这件**仍算未完**。

**平台会通知的活**：可以先等通知，但仍建议登记（防止通知丢了没人知道）。
**平台不通知的活**（另一台机器的命令、外部会话、第三方工具）：开跑当下就登记。

**② 执行人自己的报告 ≠ 独立核验**

见第 1 节。

**③ 新预计 ≠ 正式改期**

```
续期｜任务标识：M-01｜原承诺：__:__（保留）｜新预计（执行估计）：__:__
     ｜正式改期：未确认／已由____确认｜原因一句话：____｜影响：____｜仍由谁收：____
```

执行人报的新时间只是**新预计**；有权的人确认后才追加一行写明谁确认，
**原承诺那一格照旧保留**。确认前仍按原承诺算逾期。

### 6.3 只追加，不改写

状态变了就**追加一行**新状态，原行字段（尤其原预计交时、结果放哪）**原样留着**。

原因：审计要看的是**过程**，不是最终状态。改写原行等于销毁过程。

### 6.4 到点怎么查

**查的是所有未完项**，不只查「过点没人接的」：

| 当前状态 | 到了哪个节点 | 怎么处理 |
|---|---|---|
| `待收` | 该接单还没人接 | 追执行人；追不上写 `升级` |
| `已接单` | 预计交时到了 | 去结果位置看：看见 → `已收到成果`；没看见 → 追问 + `续期` 或 `升级` |
| `已收到成果` | 该验收还没核 | 按证据规则核 → `已验收` 或 `退回` |

**「到点谁来查」要写具体的人**，不写「到时候看谁在」。
他可能不在线，就在同一格写清：授权接替人 / 下次可查时间。
**实际查晚了照实记几点查的、晚了多久，不能写成已经兜住。**

### 6.5 放行后叫开工

授权 / 放行一出，**当场**叫下一棒开工，收到「已接单」或开工证据才算接住。

```
叫开工｜任务标识：____｜放行／授权摘要：（不写密钥）｜执行人：____
       ｜交付物：____｜交时：____｜对方回执：已接单（几点）／开工证据在____／尚未回
```

## 8. 常见借口（要正面回应）

| 借口 | 回应 |
|---|---|
| 「时间紧，先报完成，细节后面补」 | 细节补不上，报的就是假的。**报现状不丢人，报假话才丢人** |
| 「我看了开头，没问题」 | 整份看完，有几处出错就数清几处 |
| 「这个上次验过」 | 上次核的是哪个版本？之后改过吗？环境换了吗？ |
| 「执行人说了没问题」 | 那是指南，不是证据。收的人要看 |
| 「先标完成，验收慢慢补」 | 未完清单会失真，逾期就发现不了 |
| 「这次改动很小，不影响那边」 | 改动的实际影响面常常超出预期 |
