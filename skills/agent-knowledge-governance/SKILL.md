# 多智能体协作与知识库治理

> **一句话**：让「一个人 + 多个 AI 智能体」共同维护一套 Markdown 知识库时，**产物有归属、索引不断链、
> 经验能共享、交付有证据、错误能收敛**。

---

## 0. 这个技能解决什么

多智能体协作最常见的四种翻车方式，本技能逐个给出机制：

| 痛点 | 症状 | 本技能的机制 | 参考 |
|---|---|---|---|
| **经验不互通** | 三个智能体处理同类问题，重复踩同一个坑 | 经验回流协议：沉淀 → 加载 → 双向索引 → 查询作答 | `references/experience-reflow.md` |
| **产物散落 / 图谱污染** | 生成的文件到处飘，孤儿节点越来越多 | 产物三级分类 + 强制归档 + 孤儿清零闸门 | `references/artifact-classification.md` |
| **索引与现实脱节** | 索引写了但文件被删；文件加了但索引没更新 | 索引更新时机 + 断链扫描 + frontmatter 契约 | `references/indexing-and-links.md` |
| **「说做好了」没证据** | 子代理回报完成，实际根本没做 | 交付状态五态分离 + 证据先行五步 | `references/evidence-and-handoff.md` |

还有一条贯穿全程的：**反馈不能直接改全局规则** —— 必须经聚类 → 版本化 → 批准 → 对照四步，
避免智能体被一次偶然的吐槽带偏。见 `references/feedback-loop.md`。

## 1. 架构总览：五层真相源

一个可被多智能体共用的知识库，必须区分「什么可以改、什么不能改」。本技能用五层定位：

| 层 | 名称 | 职责 | 写入权 | 可变性 |
|:--:|---|---|---|---|
| **00** | 资源层 | 原始证据、原始素材、原始响应 | 只读 | 🚫 任何人不得覆盖 |
| **01** | 主题 Wiki | 稳定知识、方法、案例、技能卡 | 产出该卡的 agent | 🔄 演进不覆盖（版本+1） |
| **02** | 项目库 | 正在推进的问题、项目、决策 | 项目负责 agent | ✏️ 活跃可变 |
| **03** | 输出库 | 可实际使用的正式成果 | 项目负责 agent | ✏️ 批次化归档 |
| **04** | 系统维护层 | 入口、规则、状态、反馈、日志 | 单一写者（指定 agent） | 🔄 索引者统一聚合 |

**关键原则**：

- **00 层永远只读**。质量闸门第 1 项专查「资源层零覆盖」。
- **04 层单一写者**。中央索引（如 `00_总索引.md`）由一个指定的 agent 每日聚合，
  其他 agent 不得实时改写 —— 否则多人并发写索引必然冲突。
- **01 层的演进不覆盖**：改内容时 `version + 1`，旧版进归档区，保留可追溯。

> 落地时不需要照搬这套目录名 —— 关键是**五层的职责分离与写入权划分**。
> 参见 `references/five-layer-truth-source.md`（含与你现有目录结构的映射方法）。

## 2. 核心工作流

### 2.1 每次会话的标准闭环

```
① 开工前对齐   读域索引 + 历史经验 → 产出「已覆盖 / 待补充 / 可复用」三栏
② 实时记录     项目日志记过程，经验教训记坑（现象 → 原因 → 对策）
③ 收尾落盘     成果按批次归档 → 项目索引加 wikilink → 日志追加行
④ 经验回流     可复用结论 → 知识卡 → 域索引登记
⑤ 质量闸门     跑 15 项检查 → FAIL 立即修 → 归档
```

**不要跳过 ① 和 ⑤**。这两步是「多智能体」与「一堆各自为政的 agent」的分水岭。

### 2.2 开工前对齐（Step 1 展开）

在写任何代码/文档之前：

1. 读目标业务域的 `00_索引.md` —— 了解已有什么
2. 读本项目的 `索引.md` + `经验教训.md` + 历史会话索引
3. **产出三栏现状对齐**，写进本次项目日志开头：

```markdown
| 维度 | 状态 | 说明 |
|---|---|---|
| 已覆盖 | ✅ | <已有能力/已有卡片路径> |
| 待补充 | ⬜ | <缺口> |
| 可复用 | ♻️ | <可直接复用的卡/脚本/模板路径> |
```

这一步的成本是 3 分钟，收益是**避免重复造轮子**（而重复造轮子正是多智能体最大的隐性成本）。

### 2.3 收尾落盘（Step 3 展开）

```bash
# 1. 归档：L1 产物进 成果/<批次>/，L3 留 /tmp
# 2. 索引：在项目 00_索引.md 追加 wikilink（不要新建独立索引文件）
# 3. 日志：在项目 日志.md 追加本次工作记录
# 4. 验证：ls 确认文件在正确位置
```

**验证不是可选的**。子代理（subagent）的自报告不可信 —— 必须 `ls` 落盘位置，
发现放错立即 `mv`。这条规则在实践中拦下过多次「报告说归档了、实际躺在 /tmp」的返工。

## 3. 产物分级：决定什么能进知识库

三级分类，**判定标准写成可机械执行的规则**，避免「我觉得这算重要」：

| 级别 | 定义 | 进知识库？ | 位置 |
|---|---|---|---|
| **L1 最终产物** | 已交付、可复用的成果 | ✅ 必须 | `<项目>/成果/` |
| **L2 过程产物** | 中间状态、可追溯 | ⚠️ 选择性 | `成果/process/` 或仅日志 |
| **L3 临时产物** | 调试/缓存/中间计算 | ❌ 绝不打 | `/tmp` 或项目缓存目录 |

**L1 判定（满足任一即为 L1）**：

```
✅ 代码层：可运行脚本且无明显 bug / 已发布版本 / 通过测试的核心模块
✅ 文档层：用户可读的成品报告（非草稿）/ 已完成的 PPT·Word·PDF / 已上线文章
✅ 资源层：已生成并实际使用的图片·视频·音频 / 最终版备份包
✅ 知识层：已确认的调研结论（非初稿）/ 已总结的方法论·经验教训 / 已成型的索引
```

**L3 黑名单（一律不进）**：

```
/tmp/ 下任何文件 · 调试日志 · .pyc / __pycache__/ · node_modules/
.DS_Store / Thumbs.db · IDE 临时文件（.swp / *~）· .git/objects/...
构建缓存（dist/ 仅留 release 版）· 大文件（>50MB，除非是最终交付本身）
```

**边界情形**：

| 场景 | 处理 |
|---|---|
| 多版本迭代 | 只保留最终版进库，旧版靠 git history 或进归档区 |
| API 原始响应 | **绝对不进**（隐私风险），日志里只记「调用了 X，返回状态 Y」 |
| 实验性脚本 | 验证通过后升级为 L1，否则留 /tmp |
| 会话中途失败 | 已完成部分算 L1 的子集，照常归档 |

**核心原则：宁可少同步，不要乱同步。**

完整判定树见 `references/artifact-classification.md`。

## 4. 边界守卫：谁能写哪里

多智能体共用一个库最大的风险是**互相覆盖**。用「写入根目录 + 显式禁止清单」硬隔离：

```markdown
## 我的写入边界
- ✅ 只写：<my-agent-root>/  与 <shared-read-only-roots>/
- ❌ 禁止写：中央总索引（由 <single-writer> 每日聚合）
- ❌ 禁止写：其他 agent 的目录
- ❌ 禁止写：.env / auth.json / 任何含密钥的文件
- ❌ 禁止写：00 资源层（只读）
```

**跨 agent 协作的三个正确姿势**：

1. **统一项目名 + wikilink 互链** —— 同一件事在各处用同一个名字，靠链接跳转
2. **结论进共享区，过程留各自区** —— 知识库记「结论」，项目日志记「过程」
3. **中央索引由单一写者聚合** —— 其他 agent 提交条目，不直接改索引

> ⚠️ **实战坑**：同一个 vault 里存在两套同名根目录（例如 `WorkBuddy智能体日志/` 与
> `智能体协作治理/WorkBuddy智能体日志/`）时，写入前**必须**先查同步协议确认权威路径。
> 写错分支会造成「文件存在但索引找不到」，且图谱上看不出问题。
> 详见 `references/pitfalls.md`。

## 5. 索引与 wikilink 规范

### 5.1 禁止独立索引文件

**除非跨项目资源，否则禁止新建 `文件索引.md` / `图片索引.md` 这类独立 MD。**
必须通过**已有项目索引内的嵌 wikilink** 关联。

原因：Obsidian 的图谱视图里，每个独立索引文件都是一个**孤立的入口节点**，
几十个索引文件 = 几十个散落节点，图谱失去意义。

**正确做法**：在已有的项目 `00_索引.md` 里加一行 wikilink；跨项目资源才建独立索引。

### 5.2 孤儿清零是硬指标

> **任何时候孤儿文件数 > 0，必须立即执行修复流程。不允许「稍后再修」。**

**孤儿定义**：在 vault 中存在，但没有任何其他文件通过 wikilink 指向它。

修复流程：

```bash
# 1. 找出孤儿（没有入链的 md）
python3 scripts/check_orphans.py <vault-root>

# 2. 逐个处理：加链接到合适的索引 / 合并到主卡 / 确认是废弃则归档
# 3. 重跑，确认 orphan_count == 0
```

### 5.3 frontmatter 契约

每张卡片都应有统一字段，便于脚本检查与聚合：

```yaml
---
title: <卡片标题>
type: <知识卡 | 项目卡 | 决策卡 | 成果卡 | 反馈卡 | 进化提案 | 实践笔记>
status: <active | draft | archived | blocked>
owner: <负责人>
created: YYYY-MM-DD
updated: YYYY-MM-DD
source: <来源URL | 路径 | 会话ID>
confidence: <high | medium | low>
sensitivity: <public | internal | confidential | secret>
version: 1.0
effective_date: YYYY-MM-DD
review_date: YYYY-MM-DD      # 默认 effective_date + 90 天
tags: [tag1, tag2]
---
```

**最低要求**：`title` / `type` / `status` / `created` / `updated` / `source` / `tags`。
质量闸门第 3、4、5 项会检查其中若干项。

### 5.4 版本语义化

`主.次`：小修 `1.0 → 1.1`；重构 `1.x → 2.0`。
合并内容时在主卡 `source` 字段注明**所有**被合并文件名，旧版进归档区。

详见 `references/indexing-and-links.md`。

## 6. 证据先行：交付状态分离

多智能体协作里最容易糊弄过去的一环是「谁说做完了」。

### 6.1 五状态分离

| 状态 | 含义 | 还在未完清单？ |
|---|---|---|
| `待收` | 活已派出，还没确认接下 | 在 |
| `已接单` | 确认接下，**成果还没到** | 在 |
| `已收到成果` | 交付物到了约定位置，**还没核** | 在（待核） |
| `已验收` | 核过了，可交下一棒或关闭 | **不在了** |
| `已取消` | 有权的人拍板不做 | **不在了** |

另有三种过程行：`续期`（不改原承诺）、`升级`（过点追不上）、`退回`（核了没过）。

**核心是把「执行人说好了」和「收的人亲眼核过」分成两个不可混淆的状态。**

### 6.2 三条必须写死的反模式

1. **等待结束 ≠ 成果回来**
   后台命令退出、对方说「好了」，都**不等于**完成。必须去结果该在的地方看，
   看见了才记「已收到成果」，看不见就查是失败还是丢了 —— 这件**仍算未完**。

2. **执行人自己的报告 ≠ 独立核验**
   执行人报告只能当**线索**。收的人（或指定核验人）必须亲手打开看、播放、重算、
   按原步骤再走一遍。

3. **新预计 ≠ 正式改期**
   执行人报的新时间只是**新预计**；有权的人确认后才追加一行写明谁确认，
   **原承诺那一格照旧保留**。确认前仍按原承诺算逾期。

### 6.3 有效证据的定义

> 你（或指定核验人）**亲手拿到的**，而且它核的**版本、范围、环境**，
> 和你现在要说的这句话**对得上**。

- **可复用**：上次核过、之后没改、没失败过、环境没换 → 复用时写明是哪次核的、哪个版本
- **要补核**：之后有改动 / 有过失败 / 换了环境 → 只补核受影响部分
- **不算证据**：别人说好了的、核的是旧版本或别的范围的、「应该没问题」的

**照字面躲开这条规矩（换个说法暗示做完了），和违反它是一回事。**

### 6.4 开口前的五步

1. **想清楚**：哪件事能证明我要说的这句话？
2. **拿证据**：有对得上当前版本的有效证据就复用（写明出处）；没有就亲手完整做一遍
3. **看完结果**：整份看完，不只看开头几行；有几处出错就数清几处
4. **对照**：结果真能撑住我要说的话吗？撑不住就照实说现在到哪一步
5. **再开口**

完整对照表（不同交付物要什么证据）见 `references/evidence-and-handoff.md`。

## 7. 反馈闭环：从吐槽到规则

### 7.1 铁律

> **除事实错误和安全问题外，一次反馈不得直接改全局规则。**
> 必须经 **聚类 → 版本化 → 批准 → 对照** 四步。

理由：一次偶然的吐槽不等于一条通用规则。让智能体「听到一次就改」，
会让规则集迅速膨胀成互相矛盾的垃圾。

**例外**：事实错误（说错了数据）和安全问题 —— 立即修，不等聚类。

### 7.2 反馈分类

| 维度 | 取值 |
|---|---|
| 性质 | 正反馈 / 负反馈 / 缺口 / 结果数据 |
| 对象 | 事实 / 判断 / 方法 / 结构 / 表达 / 风险 / 格式 |
| 强度 | 一次（仅记录）/ 重复 ≥2 次（触发提案）/ 结果数据（立即提案） |

### 7.3 触发进化提案的条件

满足任一即触发：

1. **重复反馈**：同类反馈 ≥2 次
2. **结果数据**：有客观数据支撑（流量、验收、用户反馈）
3. **画像长期无更新**：超过 30 天未触发 → 触发审计

### 7.4 提案必须包含

- 触发证据表（反馈 ID + 日期 + 强度 + 摘要）
- 旧规则原文（注明版本号与文件路径）
- 新规则内容
- 影响评估：范围 / 风险 / 观察周期 / **回滚方案**
- 用户批准勾选框（**未批准不执行**）
- 执行记录：批准后只在原文件 `version + 1`，不覆盖原内容
- 前后对照表：旧行为 / 新预期 / 实测差异

模板见 `templates/evolution-proposal.md`。

## 8. 质量闸门（15 项）

自动化检查，让「治理」不依赖记性。脚本见 `scripts/quality_gate.sh`（bash，仅依赖 `find`/`grep`/`python3`）。

| # | 检查 | 级别 | 查什么 |
|:--:|---|:--:|---|
| 1 | 资源层零覆盖 | FAIL | 00 资源层是否被改写 |
| 2 | secret 扫描 | FAIL | 高危敏感内容（.env / key / token） |
| 3 | 来源存在 | WARN | 新文件是否带 `source:` 标注 |
| 4 | 日期有效性 | FAIL | 有无未来日期 |
| 5 | 事实/判断分离 | PASS | `type:` 标注覆盖率 |
| 6 | 不虚构实测 | FAIL | 未证实的实测声称 |
| 7 | 不重复生产旧成果 | PASS | 重复 title |
| 8 | 每轮唯一结案 | PASS | 结案一致性 |
| 9 | 抓取失败≠无新增 | PASS | 反馈库是否建立 |
| 10 | 索引一致性 | FAIL | 对话索引是否建立 |
| 11 | 状态文件一致 | FAIL | 状态配置文件是否就位 |
| 12 | 中间页≠成果 | FAIL | 草稿冒充成果 |
| 13 | 用户目标质量 | PASS | 反馈库是否运行 |
| 14 | 连续低分暂停扩量 | PASS | 连续低分信号 |
| 15 | 画像长期无更新触发审计 | WARN | 进化报告时效 |

**放行阈值：0 FAIL。** 任一 FAIL 立即回滚该批变更。

```bash
bash scripts/quality_gate.sh /path/to/vault
```

**使用纪律**（来自实战）：

> 第一次跑必然 FAIL/WARN，**必须先列出具体缺失文件**，再追求 0 WARN。
> 不要先写「完美脚本」再跑。

另有两个独立脚本：

```bash
python3 scripts/check_orphans.py <vault-root>       # 孤儿文件扫描
python3 scripts/check_links.py <vault-root>          # 断链扫描（wikilink 目标不存在）
```

## 9. 实战踩坑清单

这些都是真实跑出来的，按「症状 → 原因 → 对策」组织，完整版见 `references/pitfalls.md`。

| 症状 | 原因 | 对策 |
|---|---|---|
| 索引里有链接、点进去文件不存在 | 批量移动文件时只改了路径没改 wikilink 前缀 | 用脚本做前缀替换；移动后必跑断链扫描 |
| 文件存在但图谱上是孤立节点 | 每次新建文件没在已有索引加链接 | 归档时**必须**在已有索引加 wikilink；禁止建独立索引 |
| 同一主题出现多张重复卡 | 合并原则未执行 | 同主题合并为 1 张主卡，独有内容并入，旧版进归档区 |
| 智能体报告「已归档」但文件不在 | 依赖 subagent 自报告 | `ls` 验证落盘位置，放错立即 `mv` |
| 一次性反馈就改了全局规则 | 跳过聚类 | 走「聚类→版本化→批准→对照」四步 |
| 脚本报错但实际是环境问题 | 混淆「代码缺陷」与「环境缺失」 | `No such filter`/`command not found` = 环境缺失（可修）；断言失败 = 真缺陷 |
| 改用正则扫描 HTML 导致内容损坏 | 正则不理解 DOM 结构 | 结构化修改必须用 DOM 解析，正则只做定位 |
| 凭据进了知识库 | 归档时没过滤 | 归档前必查 `.env` / `auth.json` / key / token |

## 10. 落地清单

### 最小可用（30 分钟）

1. 建业务域目录 + 每个域一个 `00_索引.md`

8. 反馈库 + 进化提案目录 + 周进化流程
9. 孤儿/断链检查脚本接入 CI 或 cron

## 12. 适用边界

**适用**：
- 多智能体（Claude Code / Codex / Hermes / Cursor / Trae 等）共用一个 Markdown 知识库
- 需要产物可追溯、索引一致、经验共享、交付有证据
- 需要自动化质量闸门而非靠记性

**不适用**：
- 单一智能体的普通笔记管理（本技能的多智能体边界规则是多余的）
- 单文件写作 / 润色
- 与协作治理无关的内容创作（那是另一个技能的事）
