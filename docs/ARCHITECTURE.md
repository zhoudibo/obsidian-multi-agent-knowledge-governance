# Architecture · 架构与设计取舍

> 这份文档解释**为什么这么设计**，以及每个决定放弃了什么。
> 只关心「怎么做」→ 看 [SKILL.md](../skills/agent-knowledge-governance/SKILL.md) 与 [QUICKSTART.md](QUICKSTART.md)。

---

## 1. 问题的真正形态

多智能体协作的知识库，难点不在「存」和「查」，而在三件事：

1. **谁有权改什么** —— 不划边界，多个 agent 必然互相覆盖
2. **改动的后果可追溯** —— 不留过程，半年后无法回答「当时为什么这么定」
3. **一次失败不污染全局** —— 不做分层，一条吐槽就能改掉整套规则

本仓库的全部机制都是围绕这三点设计的。

## 2. 关键决策与取舍

### 决策 1：用「五层」而不是「按内容类型」组织

**备选**：按内容类型分目录（技术笔记 / 会议纪要 / 读书笔记 / 想法……）

**为什么不用**：内容类型会变、会长出交叉、无法表达「谁能改」。
一个项目目录里既有原始素材又有结论，按类型拆就散了。

**五层解决的是权限与生命周期**：谁能改、能不能改、改了怎么留痕。

**放弃了什么**：目录名不直观。新人不看文档不知道「主题 Wiki」是干什么的。
→ 补偿：`SKILL.md` 给了映射方法，且强调**不必照搬目录名**。

---

### 决策 2：产物分级写成机械规则

**备选**：写「重要成果要归档」这种自然语言规则。

**为什么不用**：自然语言规则在疲劳时会被绕过。
「这个调试日志挺重要的」——每个人都这么想过。

**机械规则的好处**：可以用脚本强制。「`/tmp` 下任何文件 → L3」
不需要判断力，只需要对照。

**放弃了什么**：有些边界情况需要人判断（如「一次会话中途失败的产物算不算 L1」）。
→ 补偿：给了边界情形处理表。

---

### 决策 3：中央索引单一写者，而不是「谁都能改」

**备选**：所有 agent 都能改中央索引，靠 git merge 解决冲突。

**为什么不用**：git merge 解决的是**文本冲突**，不是**语义冲突**。
两个 agent 同时加索引条目，merge 不报错，但条目会重复或错位 ——
而索引错误比索引缺失更危险（它让人误以为内容不存在）。

**单一写者的代价**：中央索引的更新有延迟，需要一个专门的聚合步骤。

**放弃了什么**：实时性。
→ 补偿：其他 agent 提交条目到待办区，聚合者每天处理。

---

### 决策 4：反馈必须走四步才能改全局规则

**备选**：用户说一次就改。最符合直觉。

**为什么不用**：规则集膨胀 + 单次异常被固化 + 无法回溯 + 推翻成本高。

**四步的代价**：改一条规则要等聚类、等人批准。对紧急问题太慢。

**放弃了什么**：响应速度。
→ 补偿：**事实错误和安全问题立即修**，这两类不等聚类。紧急路径保留了。

---

### 决策 5：证据分「执行人报告」和「独立核验」

**备选**：不分。执行人核过了就算。

**为什么不用**：这正是「子代理说做完了，实际没做」的根源。
执行人有强烈的完成倾向，且报告格式天然显得可信。

**分开的代价**：收的人要真的去看，多花时间。

**放弃了什么**：效率。
→ 补偿：给了「可复用证据」的条件（没改过/没失败过/环境没换 → 不用重核），
不是每次都全套重验。

---

### 决策 6：禁止独立索引文件

**备选**：每个内容类型一个索引文件。查找方便。

**为什么不用**：Obsidian 图谱里每个独立索引是一个**孤立入口节点**。
几十个索引 = 几十个散落点，图谱失去意义。而且独立索引会**分裂引用**。

**代价**：一个大索引文件会变长（几千行）。

**放弃了什么**：单文件清爽度。
→ 补偿：索引分域（每个域一个 `00_索引.md`），域内再分层。

---

### 决策 7：脚本零依赖

**备选**：用 Python + PyYAML + 各种 lint 工具。

**为什么不用**：每加一个依赖就多一类安装失败、多一类版本冲突。
多智能体环境里 agent 的运行环境各不相同，**能跑的脚本比功能全的脚本重要**。

**代价**：功能受限（没有 YAML 解析，所以 frontmatter 检查用 grep）。

**放弃了什么**：精确性。
→ 补偿：把宽松匹配写进注释，并说明「宁可少报也不误报淹没真问题」。

## 3. 数据流

```
        ┌──────────────────────────────────────────┐
        │           agent 工作目录（可写）           │
        │   项目/日志.md · 经验教训.md · 成果/<批次>/ │
        └───────────────┬──────────────────────────┘
                        │ 收尾四步（强制）
                        ▼
        ┌──────────────────────────────────────────┐
        │  ① 归档   L1 → 成果/<批次>/（含 raw/ 只读） │
        │  ② 索引   在**已有**索引加 wikilink         │
        │  ③ 日志   项目日志追加本次记录             │
        │  ④ 验证   ls 确认落盘（不信自报告）        │
        └───────────────┬──────────────────────────┘
                        │ 通用结论（换个项目还成立吗？）
                        ▼
        ┌──────────────────────────────────────────┐
        │  ⑤ 回流   知识卡 → 主题 Wiki → 域索引     │
        │            + wikilink 互链（自动反链）     │
        └───────────────┬──────────────────────────┘
                        │
                        ▼
        ┌──────────────────────────────────────────┐
        │  ⑥ 闸门   15 项 → 0 FAIL 才放行           │
        │     ├ 孤儿扫描  orphan == 0              │
        │     └ 断链扫描  broken == 0              │
        └──────────────────────────────────────────┘

  反馈路径（不直接改全局规则）：
    用户反馈 → 反馈卡（逐字保留）→ 聚类（≥2 次）
              → 进化提案（含回滚方案）→ 人工批准
              → 原文件 version+1 → 前后对照 → 无效则回滚
```

## 4. 为什么闸门是 15 项而不是 3 项

早期只做 3 项（孤儿 / 断链 / source 标注），结果漏掉了真实问题：

| 漏掉的 | 后果 |
|---|---|
| 凭据入库 | 安全事故 |
| 未来日期 | 审核时的低级错误 |
| 草稿冒充成果 | 交付质量 |
| 重复 title 的索引 | 检索混乱 |
| 中间页≠成果 | 「说做了」的另一种形式 |

但也不能无限加 —— **检查项越多，越容易为了通过而修改检查**。
15 项是权衡结果：覆盖「安全 / 一致性 / 可追溯」三类，每类都有可执行判据。

## 5. 已知限制

| 限制 | 说明 | 缓解 |
|---|---|---|
| **孤儿检测是宽松匹配** | 只要库里有同名文件就算有入链 | 宁可少报；精确模式需按路径匹配 |
| **断链检测同理** | 同上 | 会漏报同名歧义的断链 |
| **frontmatter 检查用 grep** | 只能检查字段**存在**，不能验证格式 | 格式错误靠人工 |
| **`quality_gate.sh` 是 Bash** | Windows 需 Git Bash / WSL | Python 脚本跨平台 |
| **不含实时自动化** | 定时检查、跨 agent 通知需自己接宿主能力 | 明确写在边界里，不假装提供 |
| **不含内容生产** | 不做写作/润色/选题 | 那属于另一个领域 |

## 6. 为什么选择 Markdown 而不是数据库

| | Markdown | 数据库 |
|---|---|---|
| 人可读可手改 | ✅ | ❌ |
| git 友好（diff/回滚/分支） | ✅ | ❌ |
| Obsidian 图谱与反链 | ✅ | ❌ |
| 结构化查询 | ❌ | ✅ |
| 机器写入 | ✅ | ✅ |

**关键判断**：知识库的价值主要来自**人机双向可读写**，而不是复杂查询。
「过去怎么处理过同类问题」用索引 + wikilink 反链就够，不需要 SQL。

**代价**：无法做跨库聚合统计。要统计就用 grep（脚本里就是这么做的）。
